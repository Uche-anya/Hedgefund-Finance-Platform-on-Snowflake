# Part 17: check the next-day close

**Reconciliation** means comparing our calculated records with separate records
and explaining any differences. Here the comparison statements are simulated
teaching fixtures, not statements obtained from a real broker or administrator.

Four hand-prepared files live in `fixtures/daily_references/2025-01-09/`:

| File | What we check |
| --- | --- |
| `broker_positions.csv` | Shares by portfolio and instrument, on a trade-date basis |
| `broker_cash.csv` | Settled USD cash |
| `administrator_nav.csv` | USD NAV |
| `open_obligations.csv` | Each unpaid trade's ID, payable/receivable type, due date and amount |

These files contain the separately worked figures from Part 16. They are not
generated by copying the calculation output. They still share the teaching
scenario's assumptions, so a pass is not proof of independent external accuracy.

We expect 13 Apple shares, -3 Amazon shares, USD 8,248.05 cash, a USD 720 payable,
zero receivables and USD 10,038.05 NAV. The detailed payable belongs to
SIM-D2-E001 and is due on 10 January. Cash and NAV follow the Part 16 hand arithmetic.

## Run the checks

```powershell
$activity = python -m fund_pipeline.landing --business-date 2025-01-09 --bundle daily_cash
$prices = python -m fund_pipeline.landing --business-date 2025-01-09 --bundle daily_prices
$references = python -m fund_pipeline.landing --business-date 2025-01-09 --bundle daily_references
python -m fund_pipeline.reconcile_daily --database data/gbp_publication_demo.sqlite --previous-date 2025-01-08 --business-date 2025-01-09 --delivery $activity --prices $prices --references $references
```

This requires the published opening demonstration from Part 10. Seven comparisons
should pass: two positions, cash, NAV, one detailed obligation and two obligation
totals. Share quantities must match exactly; monetary comparisons allow a one-cent
difference. The difference is always **our value minus the reference value**.

The result is saved under `data/daily_reconciliation/`, including the calculated
close, all control results, reference delivery ID/fingerprint and opening lineage.
The NAV is calculated once and that checked snapshot stays in the report.

## Deliberately make the broker disagree

```powershell
python -m fund_pipeline.reconcile_daily --database data/gbp_publication_demo.sqlite --previous-date 2025-01-08 --business-date 2025-01-09 --delivery $activity --prices $prices --references $references --demo-apple-12
```

This makes a new, explicitly labelled reference delivery where the broker says
12 Apple shares. It preserves the correct original delivery.

    Our Apple holding: 13
    Broker statement:  12
    Difference:         1 share
    Result: FAIL / BLOCKED

The cash and NAV checks can still pass. That does not cancel the position failure:
every required check must pass. The command returns exit code 1 for a blocked
result and 0 for a result eligible for review.

Missing reference rows fail rather than being treated as zero. Wrong dates,
currencies, duplicate reference keys and malformed records stop reconciliation.
Obligation details are matched individually: assigning the right total payable to
the wrong trade still fails. A header-only obligation statement is valid only
when there are no actual outstanding obligations.

## Where approval fits

The report uses the same `check_eligible` rule as the existing publication workflow.
Any failed comparison blocks eligibility; overdue obligations also block it even
when comparison records agree. The correct example is ELIGIBLE_FOR_REVIEW and
NOT APPROVED. Eligibility is a check result, not a recorded human approval.

This lesson saves reconciliation reports. It does not insert next-day candidates
into the publication database, approve them, publish them, or translate them to GBP.
[Part 18](lesson_18_daily_publication.md) now provides a separate preparation entry
point that saves these reports as review candidates and uses the existing approval
and publication commands.
